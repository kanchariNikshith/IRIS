# R3 audit and manual checks — 21 October 2026

**Verdict: R3 is partially implemented, not complete or accepted for everyday wake use.**
The detector contract, bundle validation, training/evaluation tools and bounded
single-microphone wake-to-command path exist. Normal GUI/console activation is
still click/hotkey-based. There is no selected production detector, configured
wake setting or call from VoiceController to Ears.listen_for_wake.

## Audit findings and fixes

1. **Dropped within-chunk detection:** openWakeWord's adapter returned only the
   last score when a capture chunk produced several detector frames. A .9 followed
   by .1 returned .1 and missed the hit. It now returns the peak and rejects every
   invalid intermediate score. Standard 1280-sample evaluation inputs were usually
   unaffected, but larger streaming chunks were affected.
2. **Unscored positive tail:** for a positive WAV longer than two seconds, a final
   partial 1280-sample frame could remain buffered and be discarded on reset.
   Positive tails are now padded to a complete detector frame. Negative files
   remain continuous and unpadded; observed negative duration excludes padding.
3. **Understated processing cost:** after a positive hit, the evaluator timed the
   disarmed trigger's no-op calls. It now excludes these calls, reports counted
   and skipped frames, and documents padding/timing policies. Priming remains
   excluded; these timings are not live latency, CPU or battery measurements.

Six new regression cases reproduced these issues before the fixes. The focused
detector/evaluation/handoff/preflight suite then passed 65 tests. The complete
working-tree suite passed **496 tests in 62.10s**, including ten pre-existing
greeting tests. Receipt: `data/r3-audit-21oct-tests.xml`. Dependency checks,
compileall and masked configuration preflight passed. Qt local-pipe access was
used for the GUI singleton test; no microphone or cloud call was made.
Historical model score files are preserved; their recall/timing values were
produced by the earlier evaluator and have not been recalculated in this audit.

The two-second pre-roll plus strict transcript prefix can reject a slow phrase
whose beginning has left the buffer. Wake-only speech also contributes energy to
endpointing, so the command should follow immediately in the current development
path. These are limitations to measure before activation, not verified natural
conversation behavior. R4 follow-ups and barge-in remain separate work.

The actual-model smoke receipt is `data/r3-audit-21oct-models.json`; it used the
isolated `.wake-training` environment with no microphone or owner-audio inference.


| Step | What to do | Expected result |
| --- | --- | --- |
| 1 | Wait for idle, without clicking. Say "IRIS, let's start, what time is it". | No wake response and no listening indicator: GUI wake activation is currently disabled. This checks the disabled state, not wake accuracy. |
| 2 | Click the orb or press Ctrl+Alt+Space. Wait for its listening indicator, then say "what time is it". | One capture, then processing/reply with the local time. Repeat five times; note any missing/incorrect transcript. |
| 3 | Open chat from the orb menu and type "what time is it". | Local time works independently of microphone/ASR. This distinguishes recognition problems from command routing. |
| 4 | Start capture, then use the orb's pause control. | Recording stops; paused state appears. Clicking while paused must not start capture. Resume using its local menu or typed "start listening". A paused microphone cannot hear a resume phrase. |
| 5 | Start capture, press Ctrl+Alt+Esc. | The turn stops; no late response/action should execute. Fully quit and reopen after this latched emergency stop. |
| 6 | Start capture and stay silent. | Capture ends with retry guidance instead of remaining open indefinitely. The parent recording timeout is approximately 16 seconds, with bounded cleanup; record actual time. |
| 7 | Quit IRIS. | Orb closes and microphone use ends. If available, check Windows' active microphone-use indicator, not merely its recent-access history. |

These baseline tests exercise existing R1/R2 voice behavior; passing them does not
pass R3. No supported GUI switch or end-user command currently starts the new
development handoff. Calling it manually requires a spawn-picklable local detector
factory and the appropriate isolated dependencies; that is an integration task,
not a missing setting you need to guess.

Record test step, spoken phrase, visible state, displayed transcript, response and
approximate timing. Keep private speech out of shared logs/screenshots. No new
recordings are required merely to check the implementation status.

## R3 acceptance after a qualifying model and runtime wiring exist

These checks are pending and cannot be claimed from today's GUI:

- Freeze the chosen model, compatible frontend/runtime, threshold/debounce,
  provenance and resource budgets before acceptance.
- Run at least 100 held-out natural utterances; require at least 90% recall.
  Include normal/slow/quiet speech, distances and immediate commands such as
  "IRIS, let's start, what time is it". Record detection and successful command
  transcription separately; retained audio alone does not prove ASR correctness.
- Run eight hours of representative room/media/near-miss negatives, with no
  observed false wake under the current target. Zero observed events is not proof
  of zero future risk. Do not use a one-minute result as an all-day estimate.
- Check wake-only speech produces no action, only one command follows each hit,
  pause/kill closes capture, speaker playback cannot grant permissions, and no
  second microphone stream opens. Test unplug, shutdown and sleep/resume.
- Measure phrase-end-to-hit latency and idle CPU/RAM/battery on the actual laptop.
  Validate long/slow-phrase retention and wake-to-command timing explicitly.

Until these pass, keep R3 marked **implementing** and normal ambient wake disabled.
